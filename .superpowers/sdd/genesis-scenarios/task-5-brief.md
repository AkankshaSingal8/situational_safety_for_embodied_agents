# Task 5 Brief: Fix asset-realism issues in 1a-i and 2c

## Context
Scenarios `genesis_bakeoff/scenario_1a_i.py` and `genesis_bakeoff/scenario_2c.py` were recently retrofit (commit `f43ec78`) to use real meshes instead of primitives: LIBERO's `porcelain_mug.xml`/`wine_bottle.xml` for 1a-i, and a Kenney.nl CC0 `laptop.obj` for 2c. The repo owner reviewed rendered agentview frames from these scenarios and flagged three concrete visual/physical issues:

1. **1a-i: the wine bottle should look bigger/taller than the mug, but currently doesn't.** Cross-check: `wine_bottle.xml`'s own collision-box geometry (read directly from the XML) implies a real height of roughly 22cm (neck box top at z=0.158, `bottom_site` at z=-0.06, so full height ≈ 0.218m) and a narrow ~3cm radius; `porcelain_mug.xml`'s implies roughly 10cm height and ~5-6cm radius (see `horizontal_radius_site`/`top_site`/`bottom_site` in the XML). So physically the bottle SHOULD already read as clearly taller and narrower than the mug. Since it doesn't in the render, investigate whether Genesis's MJCF import (`gs.morphs.MJCF` via `genesis_bakeoff/libero_asset_loader.py`) is correctly applying the wine bottle mesh's `<mesh ... scale="0.5 0.5 0.5">` attribute to the VISUAL mesh (the collision boxes are already absolute/final-scale, independent of this) — render/measure the actual loaded entity's visual bounding box in Genesis and compare against the XML-implied ~22cm height to confirm or rule this out. Also check whether `MUG_POS`/`BOTTLE_POS` camera framing or occlusion (bottle positioned behind/beside mug from the fixed agentview camera) is making it read as smaller than it is, independent of any scale bug — don't assume the bug is in mesh loading without first confirming it isn't just a placement/camera framing illusion. Fix whichever is actually wrong.

2. **2c: the laptop mesh is not oriented properly.** Its current placement/rotation in `scenario_2c.py` doesn't read as a laptop sitting naturally on the table (open, screen roughly upright, base flat on the table surface) in the rendered frame. Inspect `genesis_bakeoff/external_assets/laptop/laptop.obj`'s native orientation (which axis is "up" in the raw mesh, which face is the base) and correct the entity's placement `quat`/orientation in `scenario_2c.py` so it visually reads as an open laptop sitting flat on the table, hinge-side down, screen tilted back at a natural angle — not floating, not sideways, not upside-down.

3. **2c: the glass is still a bare primitive cylinder and should look like an actual glass, filled with water.** LIBERO's asset library has no glass/cup/tumbler mesh (confirmed absent — checked `stable_scanned_objects/` and `turbosquid_objects/`, neither has one). Options, in order of preference: (a) source a CC0/permissively-licensed glass or cup mesh (same sourcing pattern as the laptop — Kenney.nl or similar — stage it under `genesis_bakeoff/external_assets/glass/` with its license file, same convention as `external_assets/laptop/`), or (b) if sourcing a mesh isn't practical in this pass, build a more convincing primitive glass instead of a solid opaque cylinder: a thin-walled open-top cylinder (or a good approximation Genesis's primitive API supports) with a semi-transparent/glass-like material, PLUS a separate blue-tinted, slightly-inset, slightly-shorter cylinder inside it to read visually as water fill (not literally simulated fluid — this scenario doesn't need MPM/SPH, it's a rigid-body CBF-portability test per the existing `scenario_2c.py` docstring, just needs to look like a filled glass, not an empty cup). Whichever path you take, do not change the existing CBF hazard-zone constraint logic — that's out of scope, this is a purely visual/asset fix. If the hazard-zone geometry was tuned around the old bare-cylinder glass's dimensions, adjust it only as much as strictly necessary to stay consistent with the new glass's actual footprint.
